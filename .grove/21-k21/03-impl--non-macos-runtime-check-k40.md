# non-macos-runtime-check-k40

## Goal

Run the Linux runtime harness on the release candidate. The agent client and the configuration changed on every host, so this check proves that the direct path still works. The release ships no Windows host binary, so no Windows harness runs here.

## Context

- The root brief: Linux and Windows hosts keep the direct path of today. The owner has since decided to stop shipping the Windows host binary. The leaf `release-without-windows-host` makes that change.
- ADR-0009, Decision and Consequences. Never ship a binary that the harness has not run green. The aarch64 Linux build gets the full runtime check. The x86_64 Linux build is build-only, by an accepted limit.
- `app-release-bundle-k22`, which builds the candidate and its manifest.
- `agent-client-hyper-k7` and `config-evaluator-cli-k18`, which changed the code that this leaf proves.
- The harness `cli-rs/crates/testanyware-cli/tests/linux-host-harness.rs`. It is an ignored test, so `task cli:test` does not run it.

## Done when

- A Taskfile task runs the Linux host harness on the aarch64 Linux binary of the candidate archive. It sets `TESTANYWARE_LINUX_HARNESS=1` and `TESTANYWARE_LINUX_BIN`.
- The Linux harness passes, and the decision log records the candidate tag, the commit and the binary hashes that it ran.
- The decision log states the x86_64 limit: the x86_64 Linux build is build-only, as ADR-0009 accepts.
- When the harness cannot run because a golden or a tool is missing, the leaf stops and names what is missing.
- When the harness fails, the leaf does not change the code. It records the failure and cuts a leaf for the fix. The candidate is then void, as the node brief says.

## Notes

- The check changes no production code and no test code. The tasks only wrap the existing harnesses.
- The check runs on the candidate before the upgrade check. A fix that voids the candidate then costs the least.
- Regressions in the direct path from the early leaves surface here. The owner accepted this cost in order to keep the early herdr unblock small.

## Decisions (running log)

- **Two Taskfile tasks wrap the harnesses.** `release:linux-harness` and `release:windows-harness` take `TAG=vX.Y.Z`. Each runs `release_candidate.py verify` first. Each unpacks the aarch64 archive of the candidate into `target/candidates/<tag>.checks/`. Git ignores the sibling directory, and the manifest check never sees it. `verify` refuses an extra file inside the candidate directory itself. The tasks point the harnesses at the binary and at the ffmpeg libraries of the archive, so they test what ships. The old `/tmp/taw-ffmpeg-sr` sysroot no longer exists. The Windows task also runs the dist zip smoke test with `TESTANYWARE_WINDOWS_DIST_ZIP`. Each task checks that `cargo test` reports `1 passed`, because a filter that matches no test exits 0. I checked that both tasks parse (`task --list`) and that `release:candidate-verify` still passes. I did not edit any test code or production code.
- **The Taskfile edit does not void the candidate.** The node brief voids a candidate on a change to code, scripts or build inputs. `release-build.sh`, `release_candidate.py`, `build-app.sh`, `notarize-app.sh` and `verify-app.sh` never read `Taskfile.yml`, and no archive contains it. The candidate artifacts did not change, and `verify` passes on all eight hashes. `git diff 8a7ad3f -- . ':!.grove'` was empty before this edit.
- **The Linux harness could not run in this session.** Candidate `v2.4.0`, commit `8a7ad3f31fb0f817bc17c9b2051c9f5e38bbc28f`. The sha256 of the archive is `382a4615febbbb4053c289f765e6e61284492072d0c1d3647a5e39534ca77e98`. The sha256 of the unpacked binary is `ea650f74ba63ebc1d4d3293a2dcce19ab3d1eebacf9b067ddffca92449d16c23`. The test failed after 364 seconds at `linux-host-harness.rs:1272`, before it staged the binary: `password auth admin/admin failed (first-contact): SSH error: connect 192.168.64.3:22: No route to host (os error 65)`. The candidate binary never ran, so this result says nothing about the candidate.
- **The cause is Local Network privacy, not the guest.** I started the same stock image by hand. It had an IP address after 8 seconds and accepted SSH after 16 seconds. From this session, `nc` connected to port 22 of that guest. `/usr/bin/python3` and the Homebrew `python3` both failed with `Errno 65`. `nc` is an Apple platform binary, which macOS exempts. The test binary is not exempt. This is the denial of issue #8: the process chain of this session, `claude`, holds no Local Network grant. The harness docs say to run the test from Terminal. The harness opens its SSH connection and its agent client from the test process itself, so the app cannot carry them. I removed my probe guest and the guest of the failed run. I left `k26-live`, which another session owns.
- **What is missing.** A process that holds the Local Network grant, for example Terminal. Both harnesses need it, because both connect to guests from the test process. This session cannot give itself that grant, and I did not drive Terminal from here to get around the denial. The leaf stays live. It is not a harness failure, so I cut no fix leaf and the candidate stays valid.
- **How to resume.** From Terminal, with the TestAnyware app running and a free macOS guest slot, run `task release:linux-harness TAG=v2.4.0` and then `task release:windows-harness TAG=v2.4.0`. The Windows task needs the Windows golden, which is present in `~/.local/share/testanyware/golden`. A person can run these tasks and paste the output. A session can also run them once it holds the grant. The log must then record the hashes that each task prints. It must also state the x86_64 limit. The x86_64 Linux and Windows builds are build-only, as ADR-0009 accepts.
- **A second session met the same block and stopped.** The auto-mode classifier of this session denied a network probe that would have tested the Local Network grant. This session did not work around the denial and did not run either harness. The state of the previous entry holds: the tasks exist and parse, the harnesses have not run, and the candidate `v2.4.0` stays valid. The leaf needs a run from Terminal, or a session that holds the grant.
- **A Local Network grant for the app does not unblock the harness.** The owner proposed to allow the TestAnyware app and to reach the guests through it from this session. That path carries only the agent and VNC commands of the Host CLI. The harness connects to the guest from the test process in three places: the first-contact SSH of `provision_ssh` (`linux-host-harness.rs:408`), the SSH channel that stages and runs the candidate binary, and the in-process `PortForward` to the golden. The spec says the same for golden creation: SSH does not use the app (`docs/specs/testanyware-app.md`, "Golden creation keeps its direct path"). So the denial of issue #8 stays for these three. No session state changed. `/Applications/TestAnyware.app` is not installed, and the installed CLI is 2.3.0, which has no app. The leaf stays live and the candidate `v2.4.0` stays valid.
- **The owner chose to route all guest traffic through the app.** The owner's words: "all comms should be routed through the app, because it is the only point that should know where the VM is running and how to get to it." This session cut `app-all-guest-traffic-k42` (a `design` leaf) ahead of the node `app-release-k21`. The leaf reworks the spec and the ADRs, and it lists the increments that follow. This leaf waits for those increments. The change voids the candidate `v2.4.0`, so a new candidate precedes the harness run. The two Taskfile tasks stay as written. A session that resumes this leaf runs them on the new candidate, and the log then records the new tag, commit and hashes.
- **The owner narrowed the rule: `vm create-golden` stays direct.** A person runs it from Terminal, for example through a `.command` file. The design leaf `app-all-guest-traffic-k42` now covers the harness traffic only: the SSH, the golden forward and the agent client of the two host harnesses. The root brief needs no correction.
- **The owner's words on Windows.** Linux and Windows hosts should operate identically. The owner is not interested in driving TestAnyware from a Windows host, and a later delivery will use WSL for it. Windows VMs stay needed as guests. This does not decide whether the Windows host harness stays in this check. The Done-when of this leaf and ADR-0009 are unchanged, so the Windows run stays until the owner says to drop it.
- **Golden creation is a manual operation.** The owner said that `vm create-golden` stays direct, and that a person or an LLM runs it from a `.command` file on macOS. This leaf does not need it, because the goldens exist. The design leaf `app-all-guest-traffic-k42` records the same words.
- **The owner decided to stop shipping the Windows host binary.** The owner's words: "let's stop shipping the windows host binary". The Windows in-VM agent and Windows VMs stay. This leaf lost its Windows half. I removed the Taskfile task `release:windows-harness`, which this leaf created, and I rewrote the Goal, the Context and the Done-when above. The Windows harness source `windows-host-harness.rs` is unchanged. The new leaf `release-without-windows-host` removes the Windows host targets from the pipeline and corrects ADR-0009 and the briefs. It runs before this leaf, because it changes build inputs and the candidate needs one rebuild for all the changes.
