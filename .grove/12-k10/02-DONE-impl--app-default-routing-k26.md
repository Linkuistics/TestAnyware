# app-default-routing-k26

## Goal

Make the Host CLI route agent and VNC connections through the app by default on a macOS host. Prove it from herdr with a guest that a person started.

## Context

- `docs/specs/testanyware-app.md`, sections "How the app starts" and "New error codes", and the requirements "Every guest connection on a macOS host goes through the app" and "No client starts the app".
- The harness of `cli-app-agent-routing-k24` and the live checks in `Taskfile.yml`.
- The tests that run the CLI on macOS with explicit loopback endpoints. They assumed a direct connection.

## Done when

- On a macOS host without `TESTANYWARE_APP_SOCKET`, the CLI uses the default socket path of the app.
- A missing app bundle gives `APP_NOT_INSTALLED`, and the remedy is the setup. Nothing answering on the socket gives `APP_UNREACHABLE` with a cause. No command starts the app.
- No command falls back to a direct connection on macOS. `vm create-golden` and the lifecycle commands stay direct for now.
- Linux and Windows hosts behave as before. A test shows it.
- The existing tests that run on macOS use the harness, so they pass.
- A Taskfile live check drives a running guest from a herdr session through the development bundle. It runs `agent snapshot`, a screen capture, an input command and a file transfer.
- The leaf records the live result. A person starts the guest in Terminal and allows the alert once. The agent does the rest.

## Notes

- This leaf is the first time the default of the product changes. Run the whole suite before and after.
- The remedy text for a missing app is the five setup steps in the spec. The cask does not exist yet, so say that the release provides it.

## Decisions (running log)

- **The default.** `app_socket_for_host(env, macos_host)` in `resolve.rs` is the one rule. The variable wins on every host, and an empty value counts as unset. Without it, a macOS host gets `~/Library/Application Support/TestAnyware/testanyware.sock` from `HOME`, and any other host gets none. `app_socket_with_env` passes `cfg!(target_os = "macos")`, and `resolve_vnc_endpoint_for_host` takes the same flag. So unit tests show the Linux and Windows behaviour on this Mac: no route without the variable. No cross build of the CLI is possible here (`ffmpeg-sys-next` needs pkg-config), and the CLI has no other `cfg` for a host. With no `HOME`, the path is relative, as the VM record paths are, and the socket check names it. It never goes direct.
- **`APP_NOT_INSTALLED` is a refinement of `not_running`.** `app_route::open_stream` wraps `AppClient::open_stream`. When the error is `APP_UNREACHABLE` with cause `not_running`, the socket is the default one, and neither `/Applications/TestAnyware.app` nor `~/Applications/TestAnyware.app` exists, the error becomes `APP_NOT_INSTALLED`. A named socket never gets it, because a development bundle serves from a build directory and the CLI has no reason to look for it in `/Applications`. The decision is a pure function with an injected `exists`, and a mutation of each of its three conditions failed a test. `details` has `socket` and `searched`. The spec table says so now.
- **The remedy.** `SETUP_REMEDY` in `testanyware-app-protocol` is the five steps of the spec. It says that the release provides the cask, as the notes asked. The remedy of `APP_UNREACHABLE` with cause `not_running` or `quitting` (`START_REMEDY` of the app client) now says to open TestAnyware from `/Applications` and to turn on Start at Login. It keeps the phrase "never starts it".
- **No direct oracle on macOS, so frozen outputs.** `cli_direct` could no longer exist there. The routing tests had used it as the oracle of the output. `routed_prints` now compares each routed run with the output that the direct path printed, frozen in the test. I took the strings from the routed outputs of the current binary. At HEAD the routed and the direct output matched in all of those tests, and this leaf changes no rendering. On a Linux or Windows host, each test also runs the direct path and requires the same. The PNG test checks every pixel of the frame, and the pointer test checks the two events of a click. Those frozen values are what the direct path wrote and sent. I could not run the direct branch of any of them here, because it compiles only off macOS. I compiled it with the `cfg` widened, and I restored the files.
- **A default socket path can be too long.** The default adds 58 bytes to `HOME`, and a socket path has 103 at most. A temporary directory of macOS, with the name that `tempfile` gives it, is 58 bytes. The first run of the new tests failed with `socket_path_too_long`, and the harness now uses a short `HOME` in `/tmp` for the default socket. A real user with a `HOME` of more than 45 bytes gets the same error and cannot use the default socket. The remedy says to use a shorter path in `TESTANYWARE_APP_SOCKET`. The app has no setting for its own path outside test mode, so that remedy does not help a person yet. I left it for `config-in-app-k33`, and I did not widen this leaf.
- **A refusal came back as a pass once.** The control of the live script failed against a binary that I had mutated and not rebuilt. The mutation made a named socket give `APP_NOT_INSTALLED`. The control caught it, and I rebuilt from the restored sources and ran it again. This is also why the final measurement follows a clean build.
- **Controls seen to fail.** Three mutations, each restored: the default socket never used (4 agent tests and 1 VNC test, and 3 unit tests failed), the install check that ignores a bundle that exists (1 agent test and 1 unit test), and an install check that also judges a named socket (2 agent tests, 1 VNC test and 1 unit test). My first mutation loop passed `$T` as a command in zsh, which does not split it. It ran nothing and printed nothing, so I ran it again with a function.
- **Ignored live harnesses.** `live-vm-gate.rs` and the two host harnesses start a guest with `vm start` and then run agent and VNC commands. Those commands now need the app. Each header says so. I did not run them, because they need a guest and none runs here.
- **Source.** No framework call changed. The leaf adds no dependency.
- **Review.** I spent no in-session reviewer. The compiler, the unit tests, the integration tests with the real binaries, and the three mutations cover the decisions of this leaf.
- **The live result (2026-10-20, macOS 27.0.1, herdr pane `w2E:p1`).** A person started the guest `k26-live` in Terminal (`testanyware vm start --platform macos --id k26-live`, agent `192.168.64.2:8648`). `task app:routing-live VM=k26-live` started the development bundle (`dev.antony.TestAnyware.dev`, build 0.0.1, signed by team `TA43A4RUP3`) with `open -n -g`, with no variable set. **The first run failed** and the person had not yet answered the alert: the app's dial gave `CONNECTION_REFUSED`, cause `host_unreachable`, errno 65, and the script named no denial. The person then allowed the alert, and **the second run passed**: `agent snapshot` (5 windows), `screen capture` (1920x1080 PNG), `input move`, and a file upload and download of 200000 bytes that came back byte-equal. The control passed: with `TESTANYWARE_APP_SOCKET` naming a socket with no app, the CLI failed with `APP_UNREACHABLE`, so it has no direct path to a guest that answers. The script quit the bundle and left no socket file. The guest is still running for the person to stop.
- **What the live run does not prove.** This herdr shell could dial the guest itself (`nc -z 192.168.64.2 8648` succeeded, and so did a ping). So the premise that herdr cannot reach a guest did not hold in this session, and the success of the four commands alone does not prove that the app carried them. The proofs that it did are the integration tests (the `Host` header names the id, and no app means no dial) and the control above. The run that the root brief asks for, where herdr is refused, needs a herdr session without Local Network access, and `herdr-acceptance-run-k29` owns it.
- **Finding for the Local Network diagnosis (not changed here).** In the first run the alert was pending and the guest answered a direct `nc` from this shell. The app still reported `host_unreachable`, not `local_network_denied`, so the remedy did not name TestAnyware. The spec says that a denial is `local_network_denied` when the platform `nc` connects. Here the `nc` that the app runs had no route either, while the alert was open. I did not look into it, because the diagnosis belongs to `app-guest-streams-k23`. `app-vm-start-k27` moves the same diagnosis into the start path, so it should check whether `nc`, as a child of the app, shares the app's pending state. The remedy is what a person reads first.
